# تقرير الفحص الشامل لواجهة المستخدم وتجربة الاستخدام

**المشروع:** مكاسب رقمية  
**تاريخ الفحص:** 2026-09-03  
**نطاق الفحص:** الصفحات العامة، المقالات، المجتمع، الأدوات، لوحة المستخدم، لوحة الإدارة، والمكونات المشتركة.  
**نوع الفحص:** مراجعة ساكنة للواجهة والكود والأنماط، مع تحليل الاستجابة وRTL والإتاحة والحالات التفاعلية. لم يتضمن الفحص اختبارًا بصريًا آليًا عبر متصفح فعلي أو قياسات Core Web Vitals.

## 1. الملخص التنفيذي

الواجهة تملك هوية عربية RTL واضحة ولغة بصرية متماسكة نسبيًا: أسطح داكنة من `slate`، اللون الأخضر `emerald` كإجراء رئيسي، حدود خفيفة، وأيقونات Lucide. البنية العامة مناسبة للتوسع، وصفحات المقالات والداشبورد تمتلك تسلسلًا بصريًا جيدًا.

المشكلات الأهم ليست في غياب الهوية، بل في تفاوت تطبيقها بين المساحات، وفي بعض التفاعلات التي لا تعطي المستخدم حالة واضحة أو لا تحمي تركيز لوحة المفاتيح. أعلى المخاطر الحالية هي: لوحة الإدارة على الهاتف، عرض مؤشرات إدارية ثابتة كأنها بيانات حقيقية، أدوات تعلن وظائف بحث وتصنيف غير متاحة، ونوافذ منبثقة تحتاج إلى إدارة تركيز واتساق أفضل.

## 5. دعم RTL واللغة العربية

### 5.1 نقاط القوة

- الاتجاه العام مضبوط من الجذر، مع إعادة تأكيد `dir="rtl"` في عدد كبير من المساحات.
- المحرر الغني يضبط `direction: rtl` و`text-align: right` في CSS.
- Navbar وترتيب القوائم والأيقونات مصمم للعربية، مع استخدام `rotate-180` لبعض أسهم العودة.
- النصوص العربية في المقالات تستعمل `leading-7` و`leading-9`، وهو مناسب للقراءة.
- البريد الإلكتروني يعرض أحيانًا باتجاه LTR داخل سياق عربي، وهي ممارسة صحيحة عندما تكون القيمة نفسها LTR.

### 5.2 فجوات RTL

- لا توجد قاعدة موحدة واضحة لاستخدام `text-right`, `text-left`, `dir-ltr` و`dir-rtl`؛ بعضها يأتي من class وبعضها من attribute.
- قيم CSS مثل `left-0`, `right-0`, `ml-*`, `mr-*` موزعة في مكونات كثيرة، ما يزيد تكلفة دعم أي اتجاه آخر أو إعادة ضبط التخطيط.
- يجب اختبار الأرقام والنسب والعملات المختلطة مع العربية، خصوصًا في الأدوات المالية.
- المصطلحات الإنجليزية الطويلة داخل الشارات قد تكسر السطر أو تنتج محاذاة غير مريحة.
- بعض الأسهم تعتمد الدوران اليدوي؛ يجب توحيد دلالة اتجاه السهم في مكون Link/Action واحد.

### 5.3 معايير قبول RTL

- لا يظهر overflow أفقي عند إدخال عنوان عربي طويل أو بريد إلكتروني طويل.
- لا تتبدل علاقة الأيقونة بالنص عند تغيير حالة الزر.
- الحقول والأخطاء والـ placeholders تبدأ من الجهة الصحيحة.
- التواريخ والأرقام والعملات لها تنسيق ثابت، مع `dir="ltr"` للقيم التي تتطلبه.
- ترتيب focus بالكيبورد يتبع ترتيب القراءة من اليمين إلى اليسار.

| المكون | الحالة الحالية | النقص |

### 6.1 نتائج عالية الأولوية

- **P1: ArticleDrawer يحتاج إدارة تركيز كاملة.** يوجد [components/drawers/ArticleDrawer.tsx](../components/drawers/ArticleDrawer.tsx) مع Escape و`aria-modal` لكنه لا يحصر focus ولا يعيده إلى الزر الذي فتحه. هذا يضعف مستخدمي لوحة المفاتيح وقارئات الشاشة.
- **P1: Search modal يحتاج lock للتمرير.** [components/search/InstantSearchModal.tsx](../components/search/InstantSearchModal.tsx) يطبق focus trap لكنه لا يمنع تمرير الصفحة الخلفية، خصوصًا على الهاتف.
- **P1: رسائل النجاح والفشل غير مرئية.** عمليات الحفظ والنسخ في الحاسبات تعتمد في مواضع على console، وهذا لا يثبت للمستخدم أن الإجراء اكتمل.
- **P1: مؤشرات الإدارة تبدو حقيقية وهي ثابتة.** [app/admin/page.tsx](../app/admin/page.tsx) يعرض مبيعات، مستخدمين، نشاط خادم، ونسب تشغيل ثابتة دون توضيح أنها تجريبية. هذا خطر ثقة وقرار، وليس مجرد تفصيل بصري.
- **P1: صفحة الأدوات تعلن بحثًا وتصنيفًا غير موجودين.** [app/tools/page.tsx](../app/tools/page.tsx) يعرض عبارة “بحث + تصنيف + استخدام فوري” بينما التجربة الفعلية تعرض workspace طويلًا بلا حقل بحث أو تصفية واضحة.

## 7. الإتاحة Accessibility

### 7.1 ما هو جيد

- رابط تخطي إلى المحتوى الرئيسي موجود في layout.
- وجود `aria-label`, `aria-expanded`, `aria-controls`, `aria-modal` في عدة مكونات.
- focus-visible عام واضح.
- دعم reduced motion موجود.
- نماذج الحاسبات تستخدم labels في مواضع كثيرة.
- نتائج المجتمع تستخدم حالات live في بعض الواجهات.
- أزرار الأيقونات في Navbar والبحث لها tooltips عبر `title` و`aria-label`.

### 7.2 المشكلات

| الشدة | المشكلة | الدليل |
|---|---|---|
| عالية | Drawer بلا focus trap واستعادة focus | [ArticleDrawer.tsx](../components/drawers/ArticleDrawer.tsx) |
| عالية | Search overlay بلا body scroll lock | [InstantSearchModal.tsx](../components/search/InstantSearchModal.tsx) |
| عالية | رسائل الخطأ/النجاح غير موحدة ولا ترتبط دائمًا بالحقل | الحاسبات ونماذج الإدارة |
| متوسطة | بعض النصوص الثانوية 10-11px | Navbar، الإدارة، الأدوات |
| متوسطة | جداول الإدارة لا توفر بديلًا دلاليًا للهاتف | [app/admin/users/page.tsx](../app/admin/users/page.tsx) |
| متوسطة | استخدام `img` أو previews في بعض المواضع يحتاج alt/تحميلًا دلاليًا ثابتًا | مناطق الصور والرفع |
| منخفضة | عناوين dialogs تعتمد أحيانًا على label بدل heading ظاهر | النوافذ المنبثقة |

### 7.3 قائمة تحقق WCAG عملية

- [ ] كل dialog يحصر التركيز ويعيده إلى trigger.
- [ ] كل dialog يملك عنوانًا ووصفًا عند الحاجة عبر `aria-labelledby` و`aria-describedby`.
- [ ] كل خطأ إدخال مرتبط بحقل عبر `aria-describedby` و`aria-invalid`.
- [ ] كل نجاح أو فشل في حفظ/نسخ يظهر في `role="status"` أو `role="alert"`.
- [ ] نسبة تباين النص العادي لا تقل عن 4.5:1.
- [ ] مناطق اللمس لا تقل عن 44x44px.
- [ ] يمكن إتمام العمليات الأساسية بالكيبورد فقط.
- [ ] لا يعتمد معنى الحالة على اللون وحده.
- [ ] اختبار VoiceOver/NVDA على Navbar والبحث والDrawer والإدارة.

**المخاطر:** لا توجد صفحة فهرس عامة مستقلة لمسار `/articles`، وبعض loading boundaries تعتمد على المسارات الديناميكية. يجب التحقق من كل الروابط الواردة من Navbar والبحث.  
**الإجراء:** توفير فهرس مقالات واضح أو توجيه رسمي، وإضافة loading/error لكل مستوى ديناميكي.

### 8.3 المجتمع: 6.8/10

**نقاط القوة:** بنية feed، تصنيفات، حالات فارغة، و`aria-live` في بعض عمليات التحميل.  
**المخاطر:** المنشورات تعرض هوية عامة مثل “عضو مجتمع” وصورة حرفية واحدة، ما يقلل الثقة والإسناد. حالات الخطأ يمكن أن تتداخل مع empty state، كما أن الحماية من تكرار طلبات pagination تحتاج وضوحًا.

**الإجراء:** عرض الاسم والصورة من profile عند توفرهما، فصل error عن empty، وتعطيل load-more أثناء الطلب.

### 8.4 الأدوات: 6.5/10

**نقاط القوة:** الحاسبات نفسها منظمة، مدخلاتها تحمل labels، والنتائج مفيدة ومباشرة.  
**المخاطر:** لا يوجد بحث/تصنيف فعلي رغم الوعد به، وعدد الأدوات الظاهر لا يعكس بالضرورة registry كاملًا. توجد حالات feedback تعتمد console. فاحص كلمات المرور يحتاج `type="password"` مع toggle رؤية.

**الإجراء:** بناء فهرس أدوات من `TOOLS_REGISTRY`، إضافة بحث وتصنيف فعلي، ورسائل toast للحفظ والنسخ، وضبط الخصوصية في المدخلات.

### 8.5 لوحة المستخدم: 7.0/10

**نقاط القوة:** IA واضحة: ملخص، أدوات، محفوظات، تحليلات، إعدادات، ودعم.  
**المخاطر:** بعض المساحات كثيفة، وتوجد صور profile في واجهات تفاعلية تحتاج حالات تحميل/فشل أوضح. يجب اختبار التبويبات على 320px.

**الإجراء:** تقليل النصوص الثانوية الصغيرة، إضافة skeleton للمعلومات، وتوحيد حالات عدم وجود بيانات.

### 8.6 لوحة الإدارة: 5.8/10

**نقاط القوة:** تقسيم وظيفي واضح إلى محتوى، مستخدمين، أدوار، دعم، سجلات وإعدادات.  
**المخاطر:** sidebar كامل على الهاتف، غياب active state في [app/admin/layout.tsx](../app/admin/layout.tsx)، جدول المستخدمين غير ملائم للهاتف، ومؤشرات ثابتة توحي ببيانات حية.

**الإجراء:** تحويل sidebar إلى drawer أو tabs responsive، إضافة active route، اعتماد جدول قابل للتمرير أو بطاقات، وربط KPIs بمصدر بيانات أو وسمها بوضوح كـ demo.

## 9. الصور والأصول

### الحالة

- استخدام `next/image` و`AppImage` في مساحات مهمة جيد للأداء.
- `remotePatterns` مقيدة إلى Supabase وUnsplash، وهو قرار صحيح أمنيًا.
- fallback الافتراضي في [components/ui/AppImage.tsx](../components/ui/AppImage.tsx) هو شعار المنصة، لكنه ليس دائمًا fallback دلاليًا مناسبًا لصورة مقال.
- معاينة الرفع تستخدم blob URL؛ يجب استدعاء `URL.revokeObjectURL` عند تبديل المعاينة أو unmount.
- بعض الصفحات أو المكونات القديمة قد تحتاج مراجعة مستمرة لمنع عودة `<img>` الخام.

### معايير الصور

- [ ] كل صورة محتوى لها alt وصفي، والصورة الزخرفية لها alt فارغ.
- [ ] كل صورة `fill` داخل حاوية `relative` ذات aspect ratio ثابت.
- [ ] الصور المهمة فقط تستخدم `priority`.
- [ ] fallback المقال مختلف دلاليًا عن fallback avatar.
- [ ] لا يحدث layout shift عند تحميل الصورة.
- [ ] يتم إلغاء blob URLs بعد الاستخدام.
- [ ] مصدر الصور الخارجي يطابق allowlist المعلنة.

## 10. التحميل والفراغ والأخطاء

### التقييم

| الحالة | التغطية | الحكم |
|---|---|---|
| Loading | موجود في [app/articles/loading.tsx](../app/articles/loading.tsx) وبعض المسارات | متوسطة |
| Empty | موجود في المقالات والمجتمع والإدارة | جيدة لكن غير موحدة |
| Error boundary | موجودة على مستوى التطبيق وبعض المسارات | متوسطة |
| Pending action | غير موحدة في CRUD والحاسبات | ضعيفة |
| Success feedback | موجود جزئيًا | ضعيفة |
| Retry | موجود نصيًا في بعض المواضع | غير موحد |

### نظام حالات موحد مقترح

لكل عملية async يجب تعريف الحالات التالية بصريًا وسلوكيًا:

1. `idle`: الزر عادي.
2. `pending`: الزر disabled مع spinner ونص واضح.
3. `success`: status/toast قصير قابل للقراءة.
4. `error`: رسالة مفهومة مع الإجراء التالي أو retry.
5. `empty`: شرح مختصر وإجراء أساسي، وليس مجرد مساحة فارغة.
